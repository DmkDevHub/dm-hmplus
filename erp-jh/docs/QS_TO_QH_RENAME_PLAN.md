# QS → QH 명칭 변경 계획

> 작성일: 2026-11-13 · 원본: JH `JH202610` · 대상: vplus `VPLUS202611A` (192.168.1.25:1521:ORCLU)
> 이전 계획: [TQS_MIGRATION_ROADMAP.md](TQS_MIGRATION_ROADMAP.md) · 이전 결과: [TQS_MIGRATION_RESULT.md](TQS_MIGRATION_RESULT.md)
> 이 문서의 수치는 두 DB를 조회만 해서 확인했다. 아직 DB는 바꾸지 않았다.

## 1. 배경

- 이관한 객체의 이름을 `QS`에서 `QH`로 바꾸기로 했다(2026-11-13).
- 이관 대상, 데이터 복사 범위, 제외 객체, 소스 수정(`SEND_SMS_Q`)은 이전 계획 그대로 둔다. **이름만 바뀐다.**
- 0장 원칙도 그대로다. vplus의 기존 객체는 바꾸지 않고, JH의 객체를 vplus에 추가만 한다. JH는 읽기만 한다.

### 현재 vplus 상태 (2026-11-13 13:25 되돌리기 후)

| 객체 | 상태 |
|---|---|
| 이관한 테이블 108, 함수 12, 프로시저 275 | **삭제됨**(`07_rollback`) |
| TYPE `QSSITEOBJ01`, `QSSITETAB01` | **삭제됨**(13:46, 6장 결정 2) |
| 기존 vplus 객체 | 이관 전 기준선과 같음 |

## 2. 변경 규칙

| 대상 | JH 원본 | 이전 계획 | **새 이름** | 예시 |
|---|---|---|---|---|
| 테이블 | `TQSA_*` | `TQSB_*` | **`TQHA_*`** | `TQSA_RISK_CHK` → `TQHA_RISK_CHK` |
| 테이블 | `TQSB_*` | `TQSC_*` | **`TQHB_*`** | `TQSB_RISK_CHK` → `TQHB_RISK_CHK` |
| PK(와 PK 인덱스) | | `PK_<테이블>` | **`PK_<새 테이블>`** | `PK_TQHA_RISK_CHK` |
| FK | | `FK_<부모>_TO_<자식>` | **`FK_<새 부모>_TO_<새 자식>`** | `FK_TQHA_CTP_TO_TQHA_CTPUNT` |
| 프로시저 | `PQSA_*` | `PQSB_*` | **`PQHA_*`** | `PQSA_RISK_CHK_S` → `PQHA_RISK_CHK_S` |
| 프로시저 | `PQSB_*` | `PQSC_*` | **`PQHB_*`** | `PQSB_RISK_CHK_S` → `PQHB_RISK_CHK_S` |
| 함수 | `FQSA_*` | `FQSB_*` | **`FQHA_*`** | `FQSA_GET_TELNO` → `FQHA_GET_TELNO` |
| 이름 그대로 복사하던 것 | `FQSZ_*`, `PQSZ_*`, `QSSITE*` | 이름 그대로 | **`FQHZ_*`, `PQHZ_*`, `QHSITE*`** | 아래 표. 6장 결정 1(확정) |

- **테이블, 프로시저, 함수 모두** 이전 계획 이름의 `QSB`를 `QHA`로, `QSC`를 `QHB`로 바꾼다(2026-11-13 확정).
- 결과적으로 JH 원본의 `QSA`는 `QHA`로, `QSB`는 `QHB`로 바뀌어 **JH와 끝 글자가 같다.** 예: JH `PQSA_RISK_CHK_S`가 `TQSA_RISK_CHK`를 쓰면, vplus에서는 `PQHA_RISK_CHK_S`가 `TQHA_RISK_CHK`를 쓴다.
- 이름 그대로 복사하던 5개는 `QS`를 `QH`로만 바꾼다(`FQSZ`→`FQHZ`, `PQSZ`→`PQHZ`, `QSSITE`→`QHSITE`).
- 소스 안의 이름도 같은 표로 한 번에 바꾼다. 테이블 108개와 복사하는 함수·프로시저·TYPE 289개의 이름만 바꾼다.

## 3. 바꾸지 않는 것

| 대상 | 이유 |
|---|---|
| 소스가 호출하는 **vplus 기존 QS 객체**: `FQSE_GET_AFTL_CNT`(2개 객체가 사용), `OQSA_DRM_INFO`·`OQSA_DRM_INFO_LIST`(1), `VQSZ_TRADE`(31), `VQSZ_SITEINFO`(18), `VQSZ_SUBCONT`(3), `VQSZ_CONT_INFO`(1) | vplus에 원래 있는 객체다. 이름을 바꾸면 찾지 못해 INVALID가 된다 |
| 제외한 객체(`PQSA_ZTEST`, `PQSA_ZTEST1`, `PQSZ_DATA_CLEAR_W`, vplus에 같은 이름이 있던 13개) | 이관 대상이 아니다 |
| 컬럼 이름 | 이름 규칙의 대상이 아니다 |
| 데이터 값(예: `TQSA_CKLST.COM_CD`의 `QS0730101`) | 이름이 아니라 코드 값이다. 복사하는 14개 테이블의 데이터는 그대로 옮긴다 |
| 주석 안의 옛 이름, `WITH` 절 이름(`TQSA_PRES_HS_PER` 등) | 실행과 관계없다(이전 계획과 같다) |

## 5. 진행 방법

이전 계획의 2~7단계를 새 이름으로 다시 한다. 단계마다 승인을 받는다.

1. **2단계 다시 생성**: `gen_step2.py`의 이름 규칙만 QH로 바꿔 매핑표·SQL·되돌리기 스크립트를 다시 만든다.
   - `SEND_SMS_Q`의 소스 수정(`A.WORK_CORP_CD` → `A.CORP_CD`)이 다시 생성하면 사라지므로, 생성 단계에서 같은 수정을 넣는다.
   - 치환 검증 리포트로 소스에 바꿔야 할 JH 이름(`TQSA_`/`TQSB_`/`PQSA_`/`PQSB_`/`FQSA_` 중 매핑표에 있는 것)이 남지 않았는지 확인한다.
2. **3단계**: 테이블 108, 데이터 14개 테이블(27,250건), FK 31, 코멘트.
3. **4단계**: TYPE(6장 결정 1·2에 따라).
4. **5단계**: 함수 12, 프로시저 275.
5. **6단계**: 최종 검증과 1단계 기준선 비교(1단계 기준선은 다시 저장하지 않고 그대로 쓴다. 현재 vplus는 기준선과 같다).
6. **7단계**: 결과 보고서.
